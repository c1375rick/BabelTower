## 1. 问题定义

D 组回答了"多少个面板";E 组回答"一个面板能表达几个符号"。

关键约束(不可假设):**ImageLoaded 事件本身不带 HTTP status,JS 无 URL/status 回读口**(6733/6734-A 判死)。
所以 E 组的目标不是"JS 能不能读 status",而是:**不同 HTTP 状态码是否产生可观察行为差异,足以构成可靠的多值符号**。

若结论只有 loaded / not loaded → 仍 1 bit,直接冻结 `128 panels × 1 bit = 128-bit 物理帧`,进 BTIPC v1 设计。
若 4~8 个可判别符号成立 → 128 × 2~3 = 256~384 bit(32~48 字节)/窗,重新讨论 logical frame。

## 2. 状态码矩阵(13 个)

| 组 | 码 | 服务端行为 | 预期游戏侧观察 | 预期判定 |
| -- | -- | --- | --- | --- |
| 2xx | 200/201/204/206 | 200 空 PNG(1×1) | ImageLoaded FAST(<800ms) | 同 200 基线 → 同符号 |
| 3xx | 301/302/304/307 | 302 → `/rdata?f=E<code>` | ImageLoaded LATE(≥800ms,二次请求)或静默 | 与 200 可分 → 新符号 |
| 4xx/5xx | 400/401/403/404/500 | 对应 statusCode + 短 HTML(非图) | FAST LOADED(错误体解码)或静默 | 视分布:与 200 可分或同符号 |

- 200 为基线码;201/204/206 用于验证 2xx 内部是否有差异(预期无 → 与 200 同符号);
- 307 特意测:标准上浏览器会重发 POST,引擎 image 跟随行为可能不同;
- 500 与 4xx 分开看:解码器对"服务器错误 + HTML"与"客户端错误 + HTML"行为可能不同。

## 3. 实验设计

- **13 符号 × 1 面板/符号 × 20 轮**;每轮 13 个 SetImage 同拍发射(全部唯一面板,URL 带 `round=` 击穿缓存,无覆盖冲突);
- 轮超时 12s,轮间隔 2.0s(3xx 若跟随重定向有二次请求,dt 会显著长于 2xx);
- 观测:每 bit `LOADED dt FAST|LATE`(<800/≥800)、`DUP`(同轮同码二次 LOADED)、`ROUND END missed=..`、12s 静默;
- 服务端 `EIT id=.. round=.. code=..` 逐条落底供对账;
- 判别性判据(分析器自动输出):与 200 相比——**静默**(0 loaded)✓ / **全 LATE** ✓ / **与 200 同形(全 FAST + 到达率相近)** ✗ 同符号 / **混合** 需人工看 dt 分布重叠。

## 5. 结果 → BTIPC v1 决策表

| E 组结果 | BTIPC v1 规格 |
| --- | --- |
| 仅 200/非200 可分(或仅 loaded/静默) | **128 panels × 1 bit = 128-bit 物理帧**,b/s ≈ 191(D 组) |
| 2xx 与 3xx 可分(FAST/LATE) | **2 符号/面板 → 256 bit**(3xx 位慢 ~2×,编码时把慢符号放校验/帧尾) |
| 2xx/3xx/4xx+静默 三类可分 | **≥1.58 bit/面板 → 128×2 保守冻结**(三值需 FEC 才稳,见风险) |
| 更细粒度可分 | 重新讨论 frame;每档都要求 20 轮零串扰 |

注:即使 3 类可分,3 值符号每符号信息量 = log2(3) ≈ 1.58 bit,且边界符号(混合分布)在噪声下会串扰——**除非 20 轮零串扰,否则不冒进**。

## 6. 已知风险

1. **3xx 静默风险**:6733 证明引擎跟随 302,但那是作为"高带宽实验"测的;若本实验中 3xx 静默 → 302 跟随只在特定上下文成立,3xx 组作废;
2. **4xx FAST 陷阱**:错误体可能仍触发 ImageLoaded(引擎把它当"加载完成/失败均回调")——这正是要测的;若 4xx 与 2xx 都 FAST LOADED,则该两组同符号,**但"4xx 静默 vs 2xx loaded"仍可能给出第 2 个符号**(decode 失败路径可能不回调——待证);
3. **dt 分界 800ms 是拍的**:3xx 二次请求延迟可能 <800ms 或 >800ms 抖动——分析器同时给 P50/P95/Max,判定看分布重叠不看单点;
4. **桥需重启**:`/probe_e` 是新路由(已落盘,桥进程须重启才生效);
5. 游戏内若处于加载风暴期(参照 D 组 §10.1),结果作废重跑——`/bt6734e` 只跑 1 分钟,选稳态跑。

### 8.1 判定结果

1. **2xx 符号 = 一体**:201/204/206 与 200 行为完全一致吗?不——**三者全 20/20 静默**!
   引擎 image 管线对 2xx 家族**不按码分流**:201/204/206 的响应体虽同为空 PNG,但引擎直接丢弃不回调。
   → 2xx 内部不可细分(除 200 本身),**意外死掉 3 个候选符号**;
2. **3xx 组 = 可靠的“慢符号”**:301/302/307 三码行为完全一致(逐轮 dt 互差 <200ms),
   静默仅 r5 一轮(风暴轮,见下),到达率 95%,dt P50≈2.6s 与 200(P50≈0.125s)**分布完全分离**;
   桥端证实引擎全程跟随 302(60 次 /rdata 二跳)——**跟随从始至终成立**;
3. **4xx/5xx 组 = 可靠的“静默符号”**:400/401/403/404/500 全部 20/20 静默(非图响应体直接丢弃,
   连失败回调都没有)——**与 200/与 3xx 均完全可分**;
4. **“FAST/LATE 混合”真相(重要修正)**:3xx 在 r16~r20 变 FAST(dt 83~263ms)曾疑似“热缓存期”,
   但桥端 RDATA 证明这些轮引擎**仍然跟随了重定向**(二跳照常发生)——变快的不是“跳不跳”,
   而是**二跳请求的调度延迟**(从 ~2.3s 降到 ~0.1s)。即 LATE/FAST 只是同一符号内的**时延抖动**,不是两个符号。
   协议意义:3xx 符号的 dt 上限按 5s 计(实测 Max 4715ms),**不能用 dt 界值去区分 3xx 与 2xx**;
5. **r5 风暴轮**:200 dt=6860ms(LATE)+ 全码集体缺失一轮 = D 组 §10.1 加载风暴的复现,
   通道零丢失但在风暴期需要 pause/extend,再度佐证 normal/loading 双超时设计。

### 8.2 最终符号表(BTIPC v1 采纳)

| 符号 | 状态码 | 游戏侧表现 | 时延特征 |
| -- | -- | --- | --- |
| **S0 = “快到”** | **200** | ImageLoaded FAST | P50≈125ms,P95≈402ms,Max 6860(风暴) |
| **S1 = “慢到”** | **301 / 302 / 307** | ImageLoaded,经二跳 | P50≈2.6s,Max 4715ms;引擎必跟随 |
| **S2 = “静默”** | 201/204/206/304/4xx/5xx | 无回调(12s 内) | 不可靠作为正常符号,仅可作填充/擦除 |

可判别符号数 = **2 个可靠(200 / 3xx)+ 1 个“无信息”态**。

### 8.3 对 BTIPC v1 的最终影响

- **encoding = 2 值/面板(S0/S1),不是 1 值** —— 吞吐翻倍潜力真实存在,但 S1 面板本身耗时 ~2.6s(P50),
  **收益归零**:128 面板若混用 S0/S1,整帧完成时间被 S1 拉到 ~2.6s+,
  等效 b/s = 128~256 bit / 2.6s ≈ 49~98 bit/s,**反而低于全 200 的 191 bit/s**;
- **工程决策:BTIPC v1 冻结为全 200 编码(1 bit/panel),128 panels → 128-bit 物理帧,~191 bit/s**;
- 3xx(“慢符号”)保留两个备用用途:① **ACK/NACK 单符号**(每帧尾部 1 个面板,S1=ACK,代价固定 +2.6s 但省一条出站信道);② 异步/非紧急信道(容忍秒级延迟的消息);
- 304 与 2xx 其余码同静默(引擎不遵守 HTTP 语义 304 未修改的缓存含义,直接丢弃);
- E 组闭合:**多值编码在 6726 引擎上只有“快慢静”三态,其中仅“快/慢”两态可靠携带信息,且慢态无吞吐优势 → 单面板 >1 bit 不成立**;
- 协议继续:D 组 + E 组全部参数已齐,进 BTIPC v1 规格冻结(frame/window/timeout/ordering/dedup/request_id/loading 态处理)。
